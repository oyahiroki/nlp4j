
# 「component_s:"POWER TRAIN:AUTOMATIC TRANSMISSION"」のようなクエリーに対応できない


整理すると、今回の件では **`LocalSearch` の公開APIを増やす必要はなく、Lucene Query Parser の KEYWORD フィールド処理を重点的に確認・修正する**のがよいです。

最新の `LocalSearch` は「すべての文字列クエリを Lucene Query Parser syntax として扱う」という方針になっており、`count(query)` や `aggregate(field, query, size)` が正式な入口です。 

### 修正すべき点

1. **まず `LocalAnalytics.relativeRateLucene()` は基本的に現状維持でよい**

   * 現在は

     ```java
     long countQuery = search.count(luceneQuery);

     Map<String, Long> aggregationQuery =
             search.aggregate(aggregationField, luceneQuery, size);
     ```

     となっています。
   * 現行 `LocalSearch` のAPI設計と整合しているため、ここを `countLucene()` などへ戻す必要はありません。 
   * また、通常の `relativeRate(field, value, ...)` は既に `Map<String,String>` の構造化フィルターを利用しており、Lucene Query文字列を内部で組み立てない設計になっています。これは現在のままでよいです。 
   * `allCount` のfallbackも現在は

     ```java
     search.count(null, Map.of(aggregationField, key))
     ```

     になっており、値に空白や `:` が含まれても安全です。ここも変更不要です。 

2. **最優先で `SchemaAwareQueryParser` の KEYWORD 処理を確認する**

   * 現在の `LuceneQueryBuilder` はスキーマがある場合、`SchemaAwareQueryParser` を利用しています。 
   * したがって、

     ```text
     component_s:"POWER TRAIN:AUTOMATIC TRANSMISSION"
     ```

     が失敗する場合、第一候補はここです。
   * `_s` は KEYWORD フィールドなので、引用符の中身を Text Analyzer に流して phrase query にするのではなく、

     ```text
     POWER TRAIN:AUTOMATIC TRANSMISSION
     ```

     全体を一つの Term として検索するのが自然です。
   * `TypedFieldQueryFactory` も KEYWORD 等については `TermQuery(new Term(field, value))` を返す設計です。 
   * したがって `SchemaAwareQueryParser#getFieldQuery(...)` 相当で、KEYWORDなら exact `TermQuery` にする設計を確認するのがよいです。概念的には次の形です。

```java
@Override
protected Query getFieldQuery(
        String field,
        String queryText,
        boolean quoted) throws ParseException {

    FieldTypeDef def =
            TypedFieldQueryFactory.resolveFieldType(field, schema);

    switch (def.kind()) {

    case KEYWORD:
        return new TermQuery(
                new Term(field, queryText));

    case INTEGER:
    case LONG:
    case DOUBLE:
    case DATE:
        try {
            return TypedFieldQueryFactory.newExactQuery(
                    field,
                    queryText,
                    schema,
                    zoneId);
        } catch (IllegalArgumentException e) {
            throw new ParseException(e.getMessage());
        }

    default:
        return super.getFieldQuery(
                field,
                queryText,
                quoted);
    }
}
```

重要なのは、KEYWORDについては `quoted == true` のときだけでなく、通常の

```text
model_s:SENTRA
```

も exact match とすることです。一方、TEXTフィールドは従来どおりAnalyzerを通します。

3. **`LocalSearch.count()` 単体で今回のクエリが通るかを先に確認する**
   今回は `view()` や `LocalAnalytics` から調査を始めるより、まず次が成功することを保証します。

```java
long count = search.count(
        "model_s:SENTRA AND "
        + "component_s:\"POWER TRAIN:AUTOMATIC TRANSMISSION\"");
```

ここで失敗するなら問題は `LocalAnalytics` ではなく、ほぼ Query Parser / Query Builder の層です。

逆に `count()` が成功し、

```java
search.aggregate(
        "component_s",
        "model_s:SENTRA AND "
        + "component_s:\"POWER TRAIN:AUTOMATIC TRANSMISSION\"",
        100);
```

だけ失敗するなら、aggregation request の生成・実行側を調べます。

4. **`search()` / `count()` / `aggregate()` が同じLucene Query解釈を通ることを確認する**
   同じクエリが、

   ```java
   search.search(query, 10);
   search.count(query);
   search.aggregate("component_s", query, 100);
   ```

   の3箇所で同じ意味になる必要があります。

   `search()` だけ通って `aggregate()` が通らない、という状態は避けるべきです。現在の設計思想からすると、3つとも同じ `query_string` → `SchemaAwareQueryParser` の処理を使うのが自然です。

5. **エラー時に原因を失わないよう `LocalSearchException` を確認する**
   今回Python側では

   ```text
   Failed to execute relativeRateLucene
   ```

   しか見えていません。

   Java側でも、少なくとも

   ```text
   Failed to parse Lucene query:
   model_s:SENTRA AND component_s:"POWER TRAIN:AUTOMATIC TRANSMISSION"
   ```

   のようにクエリ文字列と元例外を保持しておくと、今後かなり調査しやすくなります。

   ただしこれは主修正ではなく、診断性の改善です。

6. **既存の単純な KEYWORD テストは残し、新しい特殊文字テストを追加する**
   現在のテストでは `category_s:恋愛漫画` のような単純な KEYWORD 検索や aggregation は既に確認されています。 
   今回不足しているのは「空白＋Lucene特殊文字を含むKEYWORD値」です。

まず `LocalSearchTestCase` に、以下をまとめて確認するテストを追加するのがよいです。

```java
public void testKeywordQuotedValueWithColon001() throws Exception {

    try (LocalSearch search =
            LocalSearch.builder("en")
                    .autoAnalyze(false)
                    .build()) {

        search.addJson("""
                {"id":"1","model_s":"SENTRA",
                 "component_s":"POWER TRAIN:AUTOMATIC TRANSMISSION"}
                """);

        search.addJson("""
                {"id":"2","model_s":"SENTRA",
                 "component_s":"POWER TRAIN:AUTOMATIC TRANSMISSION"}
                """);

        search.addJson("""
                {"id":"3","model_s":"SENTRA",
                 "component_s":"WHEELS"}
                """);

        search.addJson("""
                {"id":"4","model_s":"ALTIMA",
                 "component_s":"POWER TRAIN:AUTOMATIC TRANSMISSION"}
                """);

        search.commit();

        assertEquals(
                3L,
                search.count("model_s:SENTRA"));

        assertEquals(
                3L,
                search.count(
                        "component_s:"
                        + "\"POWER TRAIN:AUTOMATIC TRANSMISSION\""));

        String query =
                "model_s:SENTRA AND "
                + "component_s:"
                + "\"POWER TRAIN:AUTOMATIC TRANSMISSION\"";

        assertEquals(
                2L,
                search.count(query));

        assertEquals(
                2,
                search.search(query, 10).length);

        Map<String, Long> result =
                search.aggregate(
                        "component_s",
                        query,
                        100);

        assertEquals(
                Long.valueOf(2L),
                result.get(
                        "POWER TRAIN:AUTOMATIC TRANSMISSION"));
    }
}
```

さらに `LocalAnalyticsTestCase` には、今回の `view()` を直接再現するテストを追加します。既存の `relativeRateLucene()` テストはありますが、単純な `group:A` が中心で、今回のような引用付きKEYWORD値まではカバーしていません。 

```java
public void testRelativeRateLuceneKeywordQuotedColon001()
        throws Exception {

    try (LocalSearch search =
            LocalSearch.builder("en")
                    .autoAnalyze(false)
                    .build()) {

        search.addJson("""
                {"id":"1","model_s":"SENTRA",
                 "component_s":"POWER TRAIN:AUTOMATIC TRANSMISSION"}
                """);

        search.addJson("""
                {"id":"2","model_s":"SENTRA",
                 "component_s":"POWER TRAIN:AUTOMATIC TRANSMISSION"}
                """);

        search.addJson("""
                {"id":"3","model_s":"SENTRA",
                 "component_s":"WHEELS"}
                """);

        search.addJson("""
                {"id":"4","model_s":"ALTIMA",
                 "component_s":"POWER TRAIN:AUTOMATIC TRANSMISSION"}
                """);

        search.commit();

        LocalAnalytics analytics =
                new LocalAnalytics(search);

        String query =
                "model_s:SENTRA AND "
                + "component_s:"
                + "\"POWER TRAIN:AUTOMATIC TRANSMISSION\"";

        AnalyticsResult result =
                analytics.relativeRateLucene(
                        query,
                        "component_s",
                        100);

        assertEquals(2L, result.getCount());
        assertEquals(4L, result.getTotalCount());

        assertEquals(1, result.getBuckets().size());

        AnalyticsAggregationBucket bucket =
                result.getBuckets().get(0);

        assertEquals(
                "POWER TRAIN:AUTOMATIC TRANSMISSION",
                bucket.getKey());

        assertEquals(2L, bucket.getCount());
        assertEquals(3L, bucket.getAllCount());

        assertEquals(
                4.0 / 3.0,
                bucket.getRelativeRate(),
                0.000001);
    }
}
```

ここで relativeRate は、

```text
targetRate = 2 / 2 = 1.0
allRate    = 3 / 4 = 0.75

relativeRate = 1.0 / 0.75
             = 1.333333...
```

となります。

加えて、余裕があれば KEYWORD 値について `"POWER TRAIN"`、`"A:B"`、`"A:B:C"`、`"SERVICE BRAKES, HYDRAULIC:PEDALS AND LINKAGES"`、配列型の `_s` フィールドでも同じ検索ができることをテストしておくと、NHTSAのような実データにかなり強くなります。特に `:`、空白、カンマ、括弧は実データで普通に出てくるため価値があります。

結論としては、**今回変更の中心は `LocalSearch` APIそのものではなく、`SchemaAwareQueryParser` の KEYWORD exact-match 処理です**。まず `count()` → `search()` → `aggregate()` → `LocalAnalytics.relativeRateLucene()` の順で回帰テストを追加すると、どのレイヤーで壊れているか非常に明確になります。`LocalAnalytics` の現在の構造化filter化はむしろ正しい方向なので、その部分は維持するのがよいです。
